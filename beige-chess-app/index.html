Beige Chess App

A chess tactics trainer with ELO-bracketed, motif-specific puzzle practice, served live from a 2.95-million-puzzle Lichess dataset on a two-plane AWS backend.

Cognito Lightsail DynamoDB Lambda API Gateway Terraform Capacitor GitHub Actions
Technical deep-dive → Live site ↗ App Store ↗

The app is live on the iOS App Store, and the web version runs at puzzles.beigechessapp.com. This is the only project here without a public repository. It is a shipped App Store product rather than a portfolio build, so the source stays private. The app is free to download, and the architecture, data pipeline and CI/CD are documented in the technical deep-dive. I'm happy to walk through the code on request.

The Problem

Lichess and Chess.com both have large puzzle databases, but neither lets you practise a specific weakness at your own level. If I keep missing discovered attacks at a 1700 rating, I can't ask either site for "200 discovered-attack puzzles rated around 1700" and work through them in a row. You get whatever the algorithm serves next, tagged with Lichess's crowd-sourced themes. Those themes are useful, but I couldn't verify them myself.

Beige is built to fill that gap. Every puzzle is re-tagged by a pipeline I wrote (motifs, special moves, pawn structure and game phase), derived from replaying the solution moves with python-chess rather than from Lichess's Themes column. The app then lets you filter by ELO bracket and motif.

What It Does

Rated Play serves puzzles at your current level using an expected-score-scaled ELO (starting at 600, no ceiling assumed) so the rating stays meaningful as you improve. Unrated Play has a single-select ELO bracket wheel (600–3000 in 100-point steps) and a single-select motif wheel (forks, pins, mates, skewers, discovered attacks), so you can practise one combination, such as "1800 ELO, discovered attacks", as many times as you want.

Player Insights tracks per-motif, per-phase, and per-piece solve accuracy separately from the main ELO, plus a day-streak and a monthly solved/attempted trend. Lichess sync links an existing Lichess account and seeds your starting ELO from your real puzzle rating instead of a hardcoded default. A guest mode lets anyone play with local progress only and no account. I added it so an App Store reviewer without a demo account could use the app (see below).

It shipped to the iOS App Store as Beige. Android packaging exists (same Capacitor wrapper) but hasn't been submitted to the Play Store yet.

Architecture Overview

The app has two workloads with different requirements, and I deployed them separately: a high-volume, latency-critical read plane serving the anonymous puzzle catalog, and a low-volume, spiky write plane handling per-user accounts, progress and Lichess import.

The read plane is the local prototype's server.py plus a SQLite catalog, deployed to a Lightsail container service with no ALB and no VPC to design. The write plane is API Gateway with a Cognito JWT authorizer in front of six small Lambda functions, backed by two DynamoDB tables. The reasoning for the split is in the technical deep-dive.

Key Design Decisions

SQLite for the puzzle catalog

The catalog is filtered on several independent dimensions at once (ELO bracket, motif, game phase, piece) and then one match is picked at random. SQL indexes handle that well. DynamoDB would need a separate GSI for each query shape. I kept the 2.95-million-puzzle catalog in SQLite, queried live on every request, and used DynamoDB only for per-user data and a reference lookup table.

Lightsail instead of Fargate and an ALB

I originally planned the read plane as Fargate behind an ALB. Lightsail serves the same server.py image with HTTPS and a custom domain built in, with no ALB and no customer-managed VPC. The Lightsail read plane costs a flat ~$10/month, and the whole stack runs at about $10–15/month, compared with roughly $40/month for the Fargate plan. If catalog traffic outgrows Lightsail, moving to Fargate is still an option. It wasn't worth the extra complexity at launch.

Required Accounts, Plus a Guest-Mode Carve-Out

Accounts are required so progress syncs across devices. Sign-in is through Cognito with Sign in with Apple and Google, and the original design had no guest or anonymous path. This caused a problem in App Store review: with no demo account and only social sign-in, the reviewer had no way to test the app. I added a "Continue as Guest" path afterwards, backed by local storage only, to meet Apple's request for a way to review the app without an account.

Server-Authoritative ELO via Posted Events

The client posts an event ("solved puzzle X, rating R, win") and the server applies the ELO delta. If the client computed its own ELO locally, two devices could each apply the same history against a stale local copy and diverge. Sending events instead of computed state keeps cross-device sync consistent.

Capacitor for the mobile apps

The prototype was already a working vanilla HTML/JS/CSS app with a mobile-first layout. Capacitor wraps it as-is for the App Store and Play Store, so the UI did not need to be rebuilt for mobile.

How It Was Built

I built it in order of data dependencies. Accounts, sync and mobile packaging depended on having reliable puzzle data first.

1 · Data Pipeline

Filtered and tagged the full Lichess puzzle CSV with a Python pipeline built on python-chess FEN/move replay. Motifs, special moves, pawn structure and game phase are derived from what the solution sequence does, not from a generic board scan or Lichess's own crowd tags.

2 · Local Prototype

server.py (Python stdlib only) serving a small JSON API backed by live, parameterised SQL against a local SQLite build of the tagged dataset, plus a vanilla JS/HTML/CSS frontend with no framework and no bundler.

3 · Identity & Write Plane

Cognito user pool with Apple/Google federation, two DynamoDB tables, and Lambda functions behind an API Gateway HTTP API with a Cognito JWT authorizer. I validated it locally against DynamoDB Local before deploying anything to AWS.

4 · Terraform & Environments

The whole stack as one root module with dev/prod workspaces, remote state in S3 with native lockfile locking, and a Makefile that refuses to apply against the unnamed default workspace.

5 · CI/CD Pipeline

GitHub Actions with OIDC-assumed roles (no long-lived AWS keys as secrets), five required PR checks, and an auto-deploy workflow that rebuilds the container, applies Terraform and runs a smoke test against the deployed site after every merge to main.

6 · Mobile Packaging & Submission

Wrapped the same frontend with Capacitor for iOS and Android, worked through Apple's Distribution signing and App Review requirements (including a rejection over reviewer access, which guest mode was added to resolve), and shipped to the App Store.
