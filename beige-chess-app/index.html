Beige Chess App

A chess tactics trainer with ELO-bracketed, motif-specific puzzle practice, served live from a 2.95-million-puzzle Lichess dataset on a two-plane AWS backend.

This is the only project here without a public repository — it is a shipped App Store product rather than a portfolio build, so the source stays private. The app itself is free to download, and the architecture, data pipeline, and CI/CD are documented in full in the technical deep-dive. Happy to walk through the code directly on request.

The Problem

Lichess and Chess.com both have huge puzzle databases, but neither lets you drill a specific weakness at your own level. If I keep missing discovered attacks at a 1700 rating, there's no way to ask either site for "200 discovered-attack puzzles rated around 1700" and just work through those back to back. You get whatever the algorithm serves next, tagged with Lichess's crowd-sourced themes, which are useful but not something I could verify or trust the way I could trust my own analysis.

Beige is built around that specific gap: every puzzle is re-tagged by a pipeline I wrote myself — motifs, special moves, pawn structure, game phase — derived entirely from replaying the actual solution moves with python-chess, not from Lichess's Themes column. Then the app lets you filter by ELO bracket and motif and just play.

What It Does

Rated Play serves puzzles at your current level using an expected-score-scaled ELO (starting at 600, no ceiling assumed) so the rating stays meaningful as you improve. Unrated Play exposes a single-select ELO bracket wheel (600–3000 in 100-point steps) and a single-select motif wheel (forks, pins, mates, skewers, discovered attacks) so you can drill exactly one combination — "1800 elo, discovered attacks" — as many times as you want.

Player Insights tracks per-motif, per-phase, and per-piece solve accuracy separately from the main ELO, plus a day-streak and a monthly solved/attempted trend. Lichess sync links an existing Lichess account and seeds your starting ELO from your real puzzle rating instead of a hardcoded default. A guest mode lets anyone play with purely local progress and no account at all — added specifically so an App Store reviewer without a demo account could actually use the app (more on that below).

It shipped to the iOS App Store as Beige; Android packaging exists (same Capacitor wrapper) but hasn't gone through Play Store submission yet.

Architecture Overview

The app is really two very different workloads kept deliberately apart: a high-volume, latency-critical read plane serving the anonymous puzzle catalog, and a low-volume, spiky write plane handling per-user accounts, progress, and Lichess import.

The read plane is exactly the local prototype's server.py plus a SQLite catalog, deployed to a Lightsail container service — no ALB, no VPC to design. The write plane is API Gateway with a Cognito JWT authorizer in front of six small Lambda functions, backed by two DynamoDB tables. Full reasoning for the split is in the technical deep-dive.

Key Design Decisions

SQLite Catalog, Not DynamoDB

The catalog gets filtered on multiple independent dimensions at once — ELO bracket, motif, game phase, piece — then picks one match at random. That's exactly what a SQL index does well and exactly what DynamoDB does badly without a separate GSI per query shape. So the 2.95-million-puzzle catalog stays on SQLite, queried live on every request, and DynamoDB is reserved for per-user data and a reference lookup table — never the catalog itself.

Lightsail, Not Fargate + ALB

The read plane was originally planned as Fargate behind an ALB. Lightsail serves the same server.py image with HTTPS and a custom domain built in, no ALB and no customer-managed VPC — cutting the always-on cost from roughly $40/month down to a flat ~$10/month. If catalog traffic ever outgrows Lightsail, graduating to Fargate later is still an option; it just wasn't worth the complexity on day one.

Required Accounts, Plus a Guest-Mode Carve-Out

Accounts are required — Cognito with Sign in with Apple and Google, no guest/anonymous path in the original design — so progress syncs across devices. That decision had a real cost during App Store review: with no demo account and only social sign-in, a reviewer had nothing to test the app with. I added a "Continue as Guest" path afterward, backed purely by local storage, specifically to satisfy Apple's request for a way to review the app without an account.

Server-Authoritative ELO via Posted Events

The client posts an event — "solved puzzle X, rating R, win" — and the server applies the ELO delta, not the other way round. If the client computed its own ELO locally, two devices could each apply the same history against a stale local copy and diverge. Sending events instead of computed state is what keeps cross-device sync consistent.

Capacitor, Not React Native

The prototype was already a working vanilla HTML/JS/CSS app with a mobile-first layout. Capacitor wraps that as-is for the App Store and Play Store; rewriting it in React Native would have meant redoing a UI that already worked, for no real gain given the app has no need for anything React Native offers that the web stack didn't already have.

How It Was Built

The build order followed the data dependencies: nothing about accounts, sync, or mobile packaging mattered until the puzzle data itself existed and was trustworthy.

1 · Data Pipeline

Filtered and tagged the full Lichess puzzle CSV with a Python pipeline built on python-chess FEN/move replay — motifs, special moves, pawn structure, and game phase all derived from what the solution sequence itself does, never a generic board scan and never Lichess's own crowd tags.

2 · Local Prototype

server.py (Python stdlib only) serving a small JSON API backed by live, parameterized SQL against a local SQLite build of the tagged dataset, plus a vanilla JS/HTML/CSS frontend with no framework and no bundler.

3 · Identity & Write Plane

Cognito user pool with Apple/Google federation, two DynamoDB tables, and Lambda functions behind an API Gateway HTTP API with a Cognito JWT authorizer — validated locally against DynamoDB Local before any of it touched real AWS.

4 · Terraform & Environments

The whole stack as one root module with dev/prod workspaces, remote state in S3 with native lockfile locking, and a Makefile that refuses to apply against the unnamed default workspace.

5 · CI/CD Pipeline

GitHub Actions with OIDC-assumed roles (no long-lived AWS keys as secrets), five required PR checks, and an auto-deploy workflow that rebuilds the container, applies Terraform, and runs a live smoke test against the real deployed site after every merge to main.

6 · Mobile Packaging & Submission

Wrapped the same frontend with Capacitor for iOS and Android, worked through Apple's Distribution signing and App Review requirements (including a rejection over reviewer access, which is what guest mode exists to fix), and shipped to the App Store.
