Two-Plane Architecture

The app has two workloads with different requirements, and I deployed them separately: an anonymous, high-volume, latency-critical read plane serving the puzzle catalog, and a per-user, low-volume, spiky write plane handling accounts, progress and Lichess import.

The read plane is the local prototype's server.py plus SQLite, and it is the same code in prototype and production. I deployed it to an AWS Lightsail container service rather than Fargate behind an ALB to reduce cost and complexity. It costs a flat ~$10/month with HTTPS and a custom domain built in, and there is no ALB or customer-managed VPC to design. The write plane handles a handful of calls per session and is idle most of the time, which suits API Gateway, Lambda and DynamoDB better than the always-on, database-heavy catalog container. Lambda cold starts ruled Lambda out for the catalog, but they don't matter for the write plane: the functions are small and the calls are not latency-critical in the way that fetching the next puzzle is.

Data Pipeline & Tagging

Every puzzle's tags come from replaying its solution moves with python-chess. Motifs, special moves, pawn structure and game phase are derived from what the solution sequence does, scoped to the piece that just moved. The pipeline never reads Lichess's crowd-tagged Themes column. A quality filter (popularity ≥ 90, plays ≥ 100, rating 600–3000) is applied during extraction, which reduces the raw ~6.06M Lichess puzzles to the 2,953,517 the app serves.

The production build runs the tagging pass twice: once with the quality filter on (the served catalog) and once with it off, tagging all ~6.06M raw puzzles as a full analysed reference. The second run is needed because a user's Lichess puzzle history references the full Lichess ID space rather than the filtered subset. Importing that history needs tags for almost every puzzle Lichess has served, not only the quality-filtered set the app plays from.

Three outputs from one tagging run. The full reference build, the served catalog and the DynamoDB lookup table below all come from the same tagging run. The catalog is a filtered export of the reference build rather than a separate extraction, so a puzzle's tags are always the same in the catalog and the reference.

The puzzles-ref Lookup Table

The full reference build is loaded into a DynamoDB table, puzzles-ref, keyed by puzzleId. When a user links Lichess, the import Lambda does a BatchGetItem against it instead of re-analysing puzzles at import time. A popular puzzle that appears in 10,000 users' histories is analysed once, not 10,000 times. It also keeps the import Lambda small, with no bundled multi-gigabyte database and no python-chess dependency.

DynamoDB Schema

chess-users is a single-table design with PK/SK and on-demand billing. All access is by a known user over a time range, and the app has no cross-user queries, so the access pattern suits DynamoDB well.

chess-users
Keys
PK USER#<sub> Cognito sub; everything for a user lives under this partition
SK PROFILE | INSIGHTS | ACT#<ulid> three item shapes per user
Attributes
PROFILE: userName, createdAt, overall ELO, solved/failed counts, Lichess linkage (username + anchor ELO, never the token)
INSIGHTS: tagStats / motifStats / phaseStats, each {attempts, solved}
ACT#: one attempt (puzzleId, result, playedAt, source)
Why a ULID sort key instead of a plain timestamp? The first 48 bits are a millisecond timestamp and the rest is random, so ACT# items sort lexicographically in play order. A begins_with ACT# query returns history already ordered, with no separate index. A ULID is also globally unique without coordination. The client generates it at solve time, so it records when a puzzle was played even if the event waited in an offline queue before syncing.

puzzles-ref

puzzles-ref
Keys
PK puzzleId (S)
Attributes
the full precomputed tag set for every Lichess puzzle (~6.06M items): motifs, special moves, pawn structure, game phase

This table costs a few dollars a month in storage whether or not anyone imports Lichess history. I accepted that cost to keep the import Lambda small and to keep the lookup current without redeploying anything.

Event Model & Idempotency

The client posts an event ("solved puzzle X, rating R, win") and the server applies the ELO delta to PROFILE.userElo. If the client computed its own ELO locally, two devices could each apply the same history against a stale local copy and diverge. Sending events instead of computed state keeps cross-device sync consistent. The client can still update optimistically for immediate feedback, but the server remains the source of truth.

Writing an ACT# item uses ConditionExpression: attribute_not_exists(SK), so a replayed event (from an offline queue flushing twice, or a network retry) is a no-op instead of double-counting a solve. Lichess imports use a variant. Historical entries have no client-generated ULID, so a deterministic ID is derived from puzzleId + date instead. This gives the same idempotency guarantee and still sorts correctly alongside live-play events.

The ELO Formula

delta   = K * (actual - expected)
expected = 1 / (1 + 10^((puzzleRating - userElo) / 400))
K = 20, floored at 100, starting at 600

This replaced an earlier flat +8-on-solve / −7-on-fail delta, which did not account for a ceiling. A player who outclassed the puzzle pool kept climbing instead of levelling off near the dataset's highest ratings. The per-motif/phase/piece numbers on INSIGHTS are not an ELO. They are plain {attempts, solved} counters shown as an accuracy percentage, because the flat delta was never calibrated for difficulty in the way the main ELO is.

This scheme is rating-dependent, so it isn't commutative. Each delta depends on the userElo value at the moment it's applied, so processing the same two events in a different order gives a slightly different final number. The idempotency check above still prevents the same event from being applied twice. Only two different, near-simultaneous events on different devices can race. Per-user ordered processing (an SQS FIFO queue keyed by user) would remove that race. I haven't implemented it, because I don't think the extra component is worth adding until concurrent play on multiple devices is seen to cause drift.

Cognito & Required Accounts

Sign-in uses a Cognito user pool with Sign in with Apple and Google federated. The original design had no email/password flow and no guest path. Leaving out email/password means there is no password-reset flow to build and no credentials to store. Cognito's sub is the canonical user ID used everywhere downstream. Apple's Guideline 4.8 requires apps that use a third-party social login to also offer a login option with certain privacy protections. Sign in with Apple meets that requirement, so I built it in from the start.

Requiring accounts instead of a local-first design has two consequences. In-app account deletion is mandatory (Apple Guideline 5.1.1): DELETE /api/user has to delete both the Cognito user and every DynamoDB item under their partition, and I built it from the start. The App Privacy nutrition label also has to disclose "data collected, linked to identity" (account info, puzzle-history usage data, Lichess linkage) rather than "no data collected."

Guest mode. Because accounts were required, Apple's reviewer had no way to test the app: there was no demo account, and sign-in is social only. This led to a Guideline 2.1 rejection during App Review. I added a "Continue as Guest" path, backed by local storage only, so a reviewer (or anyone else) can use the whole app without an account. Every write-plane call already required a valid Cognito token, so guest play needed no backend changes. It was already supported by the backend but had no entry point in the UI until this change.

Terraform & CI/CD

The whole stack is one root Terraform module with dev/prod workspaces rather than separate directory trees, so both environments have the same structure with no hand-copied configuration. State is stored in S3 with Terraform's native use_lockfile locking (Terraform ≥ 1.10), so no separate DynamoDB lock table is needed. 

# backend.tf
terraform {
  backend "s3" {
    bucket       = "chess-practice-app-tfstate-xxxxxxxxxxxx"
    use_lockfile = true
  }
}

GitHub OIDC for CI credentials

CI uses a GitHub OIDC identity provider and two IAM roles, separated by which GitHub event can assume them: a read-only plan role trusted only for pull_request-triggered runs, and an apply-capable deploy role trusted only for pushes to main. No long-lived AWS access keys are stored as GitHub secrets. Each workflow run gets short-lived credentials from a narrowly scoped trust policy.

The deploy role is broader than strict least privilege for a few services whose ARNs can't easily be scoped by prefix before the resource exists. API Gateway, Cognito, Lightsail, Route 53, ACM and CloudWatch have an account-wide allow. I accepted that trade-off for a single-owner AWS account dedicated to one project. IAM is the exception: its permissions are scoped to this project's own role and policy ARNs only, never iam:*.

Required PR Checks

Branch protection on main requires five jobs to pass before merge: a lint pass for correctness only (no full style enforcement), Terraform fmt/validate plus a real read-only terraform plan posted as a sticky PR comment, a Docker build plus a smoke test run against the built container, and the write-plane Lambda tests run against a real DynamoDB Local service container in CI.

Deploy on Merge

On every push to main: download the puzzle database artefact from S3 → build and push a new container image → terraform apply with the new image ref passed as a -var override (so prod.tfvars isn't edited mid-run) → poll until the deployment reports running → re-run the same smoke test against the live site → on success only, a bot commits the new image tag back into prod.tfvars so the repo records what is deployed.

The Stale-Deploy Incident

I built this CI/CD pipeline after a production bug. The lightsail_image value in prod.tfvars pointed at a tag that Lightsail confirmed was running. However, the image behind that tag had been built from a commit that predated a response-shape change the live frontend already depended on. The client's puzzle-prefetch queue needed a puzzles: [...] array, and the deployed server was still returning a single puzzle.

Every filtered or rated puzzle fetch silently came back empty. Rated Play showed the board briefly and then returned to the puzzle-selection screen with an incorrect "no puzzles match this combination" message. This happened even with every motif and the full ELO range selected, so it initially looked like database corruption rather than a stale deploy.

I found the root cause with a direct curl comparison. The live endpoint returned a bare puzzle object, while the current server.py run locally against the real database returned puzzles. The same request gave different responses, which showed it was a stale image rather than corrupted data. It was also the third documented case of the same "commit merged ≠ deployed" gap in this project. Before this pipeline, every deploy step was manual, and it was easy to skip a step or lose track during a same-day branch merge.

I fixed it in the same session with a rebuild, push, terraform apply and a curl-verified deploy, and then built this CI/CD pipeline so the same failure can't go unnoticed again. The pipeline's smoke test (scripts/smoke_test_server.py) is a regression test for this incident. It calls the live site with the broadest filter shape that reproduced the bug and asserts a non-empty puzzles array, rather than only checking for a 200 status code.

Mobile Packaging (Capacitor)

Capacitor wraps the same index.html/app.js/ style.css as a native iOS/Android app, so there is no separate mobile codebase. One command copies the web sources into Capacitor's required www/ build directory and re-syncs both native projects.

Why API_BASE is needed. The native shell runs the bundled frontend from capacitor://localhost (iOS) or https://localhost (Android) rather than the real domain, so a plain relative /api/* call would resolve against the app's local bundle instead of the backend. API_BASE only changes behaviour when window.Capacitor?.isNativePlatform?.() is true. The web build keeps using relative paths. The CORS allowlist in server.py permits only those two native origins.

Known Limitations

I ran a separate, fuller security and architecture review of the live AWS account (IAM hygiene, CloudTrail, cost anomaly detection, rate limiting, per-Lambda IAM scoping). I plan to publish it as its own write-up once I've decided which findings to fix and which to defer. The items below are listed here because they are structural choices rather than missing configuration:

  • No rate limiting or WAF on the public read API. The catalog is served anonymously by design, since it is read-only puzzle data, and it is currently unthrottled. Nothing stops a script from sending heavy traffic and increasing compute cost.
  • All six write-plane Lambdas share one IAM execution role. That role carries a couple of permissions (such as Cognito user deletion) that only one function uses, so another function could in principle call something it doesn't need. This came from using one shared deployment package rather than from a deliberate scoping decision.
  • The Stockfish eval pass is built but deliberately not run yet. It would enable eval-based difficulty and forcing-sequence signals, but none of the current filters need it, so I've deferred it.
