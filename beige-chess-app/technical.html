Two-Plane Architecture

The app is really two very different workloads, kept deliberately separate so neither one contaminates the other: an anonymous, high-volume, latency-critical read plane serving the puzzle catalog, and a per-user, low-volume, spiky write plane handling accounts, progress, and Lichess import.

The read plane is exactly the local prototype's server.py plus SQLite — nothing about it changes between prototype and production. It's deployed to an AWS Lightsail container service rather than Fargate behind an ALB purely to cut cost and complexity: a flat ~$10/month with HTTPS and a custom domain built in, no ALB, no customer-managed VPC to design. The write plane's traffic profile — a handful of calls per session, idle most of the time — fits API Gateway + Lambda + DynamoDB far better than it fits the always-on, DB-heavy catalog container. Lambda cold starts, which correctly ruled Lambda out for the catalog, don't matter here: these functions are small and the calls aren't latency-critical the way "give me the next puzzle instantly" is.

Data Pipeline & Tagging

Every puzzle's tags come from replaying its actual solution moves with python-chess — motifs, special moves, pawn structure, and game phase are all derived from what the solution sequence itself does, scoped to the piece that just moved. Lichess's own crowd-tagged Themes column is never read anywhere in the pipeline. A quality filter (popularity ≥ 90, plays ≥ 100, rating 600–3000) is baked into extraction, which brings the raw ~6.06M Lichess puzzles down to the 2,953,517 the app actually serves.

The production build runs the tagging pass twice: once with the quality filter on (the served catalog) and once with it off, tagging all ~6.06M raw puzzles as a full analyzed reference. That second run matters because a user's Lichess puzzle history references the full Lichess ID space, not our filtered subset — importing that history needs tag coverage for essentially every puzzle Lichess has ever served, not just the quality-filtered slice the app itself plays from.

One tagging computation, three artifacts. The full reference build, the served catalog, and the DynamoDB lookup table below are all derived from the same single tagging run — the catalog is a filtered subset export of the reference build, not a second independent extraction. That means the catalog and the reference can never drift on a puzzle's tags; it's literally the same computation, just filtered differently downstream.

The puzzles-ref Lookup Table

The full reference build is loaded into a DynamoDB table, puzzles-ref, keyed by puzzleId. When a user links Lichess, the import Lambda does a BatchGetItem against it instead of re-analyzing puzzles at import time — a popular puzzle that shows up in 10,000 users' histories gets analyzed exactly once, ever, not 10,000 times. It also keeps the import Lambda tiny: no bundled multi-gigabyte database, no python-chess dependency in the Lambda at all.

DynamoDB Schema

chess-users is a single-table design, PK/SK, on-demand billing. All access is by known user, time-ranged — no cross-user queries exist in this app — which is exactly DynamoDB's sweet spot.

chess-users
Keys
PK USER#<sub> Cognito sub — everything for a user lives under this partition
SK PROFILE | INSIGHTS | ACT#<ulid> three item shapes per user
Attributes
PROFILE — userName, createdAt, overall ELO, solved/failed counts, Lichess linkage (username + anchor ELO, never the token)
INSIGHTS — tagStats / motifStats / phaseStats, each {attempts, solved}
ACT# — one attempt: puzzleId, result, playedAt, source
Why a ULID sort key, not a plain timestamp? The first 48 bits are a millisecond timestamp and the rest is random, so ACT# items sort lexicographically in play-order for free — a begins_with ACT# query returns history already ordered, with no separate index. It's also globally unique with no coordination, and the client generates it at solve time, so it reflects when a puzzle was actually played even if the event sat in an offline queue before syncing.

puzzles-ref

puzzles-ref
Keys
PK puzzleId (S)
Attributes
the full precomputed tag set for every Lichess puzzle (~6.06M items) — motifs, special moves, pawn structure, game phase

This table costs a few dollars a month in storage whether or not anyone ever imports Lichess history — an accepted trade for keeping the import Lambda tiny and the lookup always fresh without redeploying anything.

Event Model & Idempotency

The client posts an event — "solved puzzle X, rating R, win" — and the server applies the ELO delta to PROFILE.userElo, never the other way round. If the client computed its own ELO locally, two devices could each apply the same history against a stale local copy and diverge; sending events instead of computed state is what keeps cross-device sync consistent. The client can still update optimistically for instant feedback, but the server stays the source of truth.

Writing an ACT# item uses ConditionExpression: attribute_not_exists(SK), so a replayed event — from an offline queue flushing twice, or a network retry — is a harmless no-op instead of double-counting a solve. Lichess imports use a variant: there's no client-generated ULID for historical entries, so a deterministic ID is derived from puzzleId + date instead, keeping the same idempotency guarantee while still sorting correctly alongside genuine live-play events.

The ELO Formula

delta   = K * (actual - expected)
expected = 1 / (1 + 10^((puzzleRating - userElo) / 400))
K = 20, floored at 100, starting at 600

This replaced an earlier flat +8-on-solve / −7-on-fail delta, which had no ceiling-awareness — a player who outclassed the puzzle pool just climbed unbounded instead of plateauing near the dataset's real rating ceiling. The per-motif/phase/piece numbers on INSIGHTS are deliberately not an ELO at all anymore — they're plain {attempts, solved} counters shown as an accuracy percentage, since a flat delta was never difficulty-calibrated the way the main ELO is.

This scheme is rating-dependent, so it isn't commutative. Each delta depends on the userElo value at the moment it's applied, so processing the same two events in a different order lands on a slightly different final number. The idempotency check above still prevents the same event from double-applying — only two genuinely different, near-simultaneous events on different devices can race. Per-user ordered processing (an SQS FIFO queue keyed by user) would remove that residual race entirely; it isn't implemented today, on the judgment that it isn't worth the extra moving part until multi-device concurrent play is actually observed to cause drift.

Cognito & Required Accounts

A Cognito user pool with Sign in with Apple and Google federated in — no email/password flow, no guest path in the original design. Skipping email/password entirely means no password-reset flow to build and no credentials to store; Cognito's sub is the canonical user ID used everywhere downstream. Sign in with Apple isn't optional here: Apple's Guideline 4.8 requires offering it the moment you offer any other social login, so it was built in from day one rather than added under review pressure later.

Choosing required accounts over a local-first design carries two consequences that a "no accounts" version wouldn't have had. In-app account deletion is mandatory (Apple Guideline 5.1.1) — DELETE /api/user has to purge both the Cognito user and every DynamoDB item under their partition, and it was built from day one rather than retrofitted. And the App Privacy nutrition label has to honestly disclose "data collected, linked to identity" — account info, puzzle-history usage data, Lichess linkage — it can no longer claim "no data collected."

The guest-mode carve-out. Required accounts meant Apple's reviewer had nothing to test the app with — no demo account exists, and sign-in is social-only. That surfaced as a real Guideline 2.1 rejection during App Review. The fix was a "Continue as Guest" path, backed purely by local storage, added specifically so a reviewer (or anyone else) can use the whole app with no account at all. Every write-plane call was already guarded on holding a real Cognito token, so guest play needed no backend changes — it was already "supported," just unreachable through the UI until this shipped.

Terraform & CI/CD

The whole stack is one root Terraform module with dev/prod workspaces rather than separate directory trees, so both environments stay structurally identical with nothing hand-duplicated. State lives remotely in S3 with Terraform's native use_lockfile locking (Terraform ≥ 1.10) — no separate DynamoDB lock table needed. 

# backend.tf
terraform {
  backend "s3" {
    bucket       = "chess-practice-app-tfstate-xxxxxxxxxxxx"
    use_lockfile = true
  }
}

GitHub OIDC, Not Long-Lived Keys

A GitHub OIDC identity provider plus two IAM roles, distinguished by which GitHub event can assume them: a read-only plan role trusted only for pull_request-triggered runs, and an apply-capable deploy role trusted only for pushes to main. No long-lived AWS access keys are stored as GitHub secrets anywhere — every workflow run gets short-lived, narrowly-trusted credentials instead.

The deploy role is deliberately broader than textbook least-privilege for a handful of services whose ARNs aren't cheaply prefixable before the resource exists — API Gateway, Cognito, Lightsail, Route 53, ACM, CloudWatch get an account-wide allow. That's an accepted tradeoff for a solo-owner AWS account dedicated to one project. IAM itself is the one deliberately tight exception — scoped to this project's own role/policy ARNs only, never iam:*.

Required PR Checks

Branch protection on main requires five jobs to pass before merge: a correctness-only lint pass (not full style enforcement), Terraform fmt/validate plus a real read-only terraform plan posted as a sticky PR comment, a Docker build plus a smoke test run against the built container, and the write-plane Lambda tests run against a real DynamoDB Local service container in CI.

Deploy on Merge

On every push to main: download the puzzle database artifact from S3 → build and push a fresh container image → terraform apply with the freshly-pushed image ref passed as a -var override (no need to edit prod.tfvars mid-run) → poll until the deployment reports running → re-run the same smoke test against the real live site → only on success, bot-commit the new image tag back into prod.tfvars for human-readable repo truth.

The Stale-Deploy Incident

This CI/CD pipeline exists because of a real production bug, not as a precaution taken in the abstract. prod.tfvars's lightsail_image pointed at a tag Lightsail confirmed was running — but the image behind that tag had been built from a commit that predated a response-shape change the live frontend already depended on (the client's puzzle-prefetch queue needed a puzzles: [...] array; the deployed server was still returning a singular puzzle).

Every filtered or rated puzzle fetch silently came back empty. Rated Play flashed the board and then bounced back to the puzzle-selection screen with a false "no puzzles match this combination" — reproducible even with every motif and the full ELO range selected, which made it look at first like database corruption rather than a stale deploy.

Root-caused with a direct curl comparison, not by guessing: the live endpoint returned a bare puzzle object, while the current server.py run locally against the real database correctly returned puzzles. Same code, different behaviour — proof this was a stale-image problem, not corrupted data. It was also the third documented instance of the same underlying "commit merged ≠ deployed" gap in this project — every deploy step before this pipeline existed was manual, and easy to partially skip or lose track of during a same-day branch merge.

Fixed live in that session with a real rebuild, push, terraform apply, and a curl-verified deploy — then this entire CI/CD pipeline, specifically so the same failure mode can't recur silently again. The pipeline's smoke test (scripts/smoke_test_server.py) is a direct regression test for this exact incident: it hits the live site with the broadest-possible-filter shape that reproduced the bug and asserts a genuinely non-empty puzzles array, not just a 200 status code.

Mobile Packaging (Capacitor)

Capacitor wraps the exact same index.html/app.js/ style.css as a native iOS/Android app rather than maintaining a separate mobile codebase. One command copies the web sources into Capacitor's required www/ build directory and re-syncs both native projects.

Why API_BASE exists at all. The native shell runs the bundled frontend from capacitor://localhost (iOS) or https://localhost (Android), not the real domain — so a plain relative /api/* call would resolve against the app's own local bundle instead of the real backend. API_BASE only changes behaviour for window.Capacitor?.isNativePlatform?.(); the plain web build keeps using relative paths unmodified. server.py's CORS allowlist permits exactly those two native origins, nothing else.

Known Limitations

I ran a fuller security and architecture review of the live AWS account separately — IAM hygiene, CloudTrail, cost anomaly detection, rate limiting, per-Lambda IAM scoping — and I'm keeping that as its own dedicated write-up once I've worked through which findings actually get fixed versus consciously deferred. Two things are worth flagging here directly since they're structural choices, not just missing configuration:

  • No rate limiting or WAF on the public read API. Serving the catalog anonymously (by design — it's read-only puzzle data) means it's also fully unthrottled today. Nothing stops a script from hammering it and running up compute cost.
  • All six write-plane Lambdas share one IAM execution role. That role carries a couple of permissions (like Cognito user deletion) only one specific function actually uses, so in principle another function could call something it never legitimately needs. It's an artifact of one shared deployment package, not a deliberate scoping decision.
  • The Stockfish eval pass is built but deliberately not run yet. It would unlock eval-based difficulty/forcing-sequence signals, but nothing in the current filter set needs it, so it's staying deferred rather than adding scope for its own sake.
