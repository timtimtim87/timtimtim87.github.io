AWS Stock Screener

Serverless stock screener and portfolio tracker with a Telegram bot interface. Under $1/month in AWS charges.

Lambda EventBridge API Gateway S3 Parameter Store AWS SAM Python
Technical deep-dive → GitHub ↗

This stack is no longer deployed. The SAM template and Lambda code are available on GitHub.

The Problem

I had developed a systematic trading strategy that I wanted to test with a paper trading account. I needed a daily ranked list of entry signals from a large stock watchlist, and a custom view of my active positions based on my exit strategy logic. No commercial software offered the right combination.

The solution needed to be cheap to run, easy to check from my phone, and flexible enough to change as the strategy changed.

What It Does

The project had two main flows. The first ingested end-of-day price data each morning, computed the custom attributes required to generate entry signals, and stored the results in S3. The second let me query those results and view my active positions against my exit logic. Sending /daily from Telegram fetched live position data from my broker API and returned a formatted summary. A daily collection run took under 2 minutes, and the system cost under $1/month in AWS charges.

Outcome
~750 Russell 1000 stocks screened and ranked daily before market open
Top candidates delivered to Telegram on demand
Daily history of rankings and portfolio snapshots kept in S3 for local analysis
Under $1/month in AWS charges (the Polygon data subscription was the only meaningful cost)

Key Design Decisions

Decision · Compute

Lambda over EC2 or ECS. The workload runs once daily plus occasional bot queries, so it does not need always-available compute. With EC2 I would be paying for capacity I was not utilising. This usage fits within the Lambda free tier, and Lambda scales automatically. The two functions are sized differently. The data collector runs at 1,024 MB because it fetches price history for ~750 stocks and uses pandas to load and rewrite the results CSVs in memory. The bot runs at 512 MB because its work is JSON parsing and S3 reads. Lambda billing is memory × duration, so sizing each function to its actual workload keeps costs low.

Decision · Storage

S3-based file storage over RDS or DynamoDB. The smallest RDS instance costs roughly $15/month even when idle, and RDS adds VPC networking overhead. DynamoDB would require designing partition keys before knowing future analysis needs, and makes local data exploration harder. S3 storage for these files cost a few cents a month, and I could download the files for local analysis whenever I needed them. The data access pattern is append-only writes and occasional full reads.

Decision · Credentials

Parameter Store over environment variables or Secrets Manager. Parameter Store integrates natively with Lambda via IAM, includes KMS encryption, and costs nothing for standard parameters. The Lambda functions fetch API keys at runtime. The API keys were never hardcoded, never committed to git, and never saved in plaintext environment variables. Secrets Manager would be the right choice if rotation were needed. For static API keys, Parameter Store is the simpler and cheaper option. IAM access is scoped to the /screener/* parameter path rather than all of Parameter Store. S3 access is scoped to the specific bucket ARN. The Telegram bot also performs application-level authorisation: each incoming message has its chat_id validated against an authorised value stored in Parameter Store. Requests from unrecognised chat IDs are rejected before any data is fetched.

Decision · Bot Trigger Model

Webhook mode over polling. In polling mode, a long-running process continuously calls Telegram's API to ask for new messages, which requires always-on compute. In webhook mode, Telegram calls the API Gateway endpoint as soon as a message arrives (what I type in Telegram), and Lambda handles it and shuts down.

Decision · No VPC

Lambda without VPC attachment. Lambda accesses S3 and Parameter Store through AWS service endpoints without a VPC. Adding a VPC would require a NAT Gateway (~$33/month) or VPC endpoints (~$7/service/month) for outbound access. For this workload, VPC deployment adds cost and networking complexity without materially improving the security posture.

Where This Design Breaks Down

This architecture suits scheduled batch ingestion, low-frequency query traffic, and file-oriented analytics. It would stop being the right fit in these cases:

  • Query volume increased substantially. Reading full CSVs on every bot request does not scale. A metadata index or DynamoDB layer for keyed lookups would be the next step.
  • Latency became critical. Lambda cold starts and S3 reads add up. A warm cache layer would help.
  • The data model grew more complex. CSV works well for flat tabular data. Parquet with Athena would be a better fit for larger datasets with ad hoc query needs.
  • The /trigger command is fragile. It finds the collector Lambda by scanning all functions in the account and matching on the function name. Renaming the collector function would break /trigger silently, with no error. The correct approach is to pass the collector's ARN as an environment variable at deploy time, which makes the dependency explicit.

What I'd Do Differently

  • Data validation and alerting. When the Polygon subscription lapsed, the Lambda did not fail. It ran, processed data for 0 stocks, and reported success. Two changes would address this. The first is to validate that the ingested data has today's date before writing to S3. The second is to publish a stocks_analyzed metric to CloudWatch on each run, with an alarm that fires if the value drops to zero or the function has not run within the expected window.
  • Resource tagging from day one. Running multiple projects in one account without tagging makes cost attribution impossible. Each project should have been in its own account, or at minimum every resource should have been tagged with a project identifier.
  • S3 versioning strategy. Versioning was enabled without a lifecycle policy. Each daily run rewrote the CSV files in full (including the appended ones), and every previous copy was kept as a non-current version, so bucket storage kept growing every day. A lifecycle policy to expire non-current versions after 1 day should have been configured at creation.
