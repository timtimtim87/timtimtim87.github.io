Full-Stack Product · Client Onboarding System

PT-Engine

Client onboarding and reporting engine for my personal-training practice. A new client fills in one form; the coach gets a structured, AI-assisted report before the first session.

The Problem

Onboarding a new coaching client is the most information-dense moment of the relationship, and traditionally the most wasteful. The first session gets eaten by an intake conversation, the answers live in the coach's head or in scattered notes, and the quality of the first program depends on how good that one conversation happened to be. It doesn't scale past a handful of clients, and nothing about it is repeatable.

I wanted every new client to arrive at their first session already understood: goals, injuries, medical history, eating patterns, sleep, stress, and an honest self-assessment of their current habits, all captured before we ever meet, and turned into a report both of us can work from.

The second requirement was operational: this is a working tool for a real business run by one person. Hosting had to be simple, reliable, and close to free, with no servers to patch and nothing to babysit.

What It Does

The coach logs in, adds a client, and sends them a magic link. The client fills in a two-sheet intake with no account and no password: one sheet of specifics (goals, injuries, medical history, what they actually eat, training and life logistics) and one sheet of 1-to-10 self-ratings across nutrition, sleep, stress, and movement, each with an optional one-line note in their own words. On submit, the engine scores the ratings deterministically, two AI agents interpret the free text, and a structured report is stored and rendered for the coach. After onboarding, each client gets one reusable weekly check-in link, and a third agent writes a coach-only trend read on every submission.

Outcome
Client onboarding runs without the coach present, from a single link
Coach-ready report generated within a minute of the client submitting
Every report readable in two voices: coach (clinical, third person) and client (second person)
Weekly check-ins on one reusable link per client, with an AI trend narrative
Every AI call logged with prompt version, tokens, cost estimate and request id
Hosting and database run in managed free tiers; AI costs are cents per client

The Onboarding Flow

The whole product is one loop. The interesting architecture is not the hosting, it's how the work is split between deterministic code and AI.

(Clerk-protected)                  (magic link, single-use)
      │                                   │
  add client ──── intake link ───────────►│
      │                                   │
      │                        two-sheet intake form
      │                        (specifics + self-ratings)
      │                                   │
      │                                   ▼
      │                          POST /api/intake/submit
      │                                   │
      │              ┌────────────────────┼────────────────────┐
      │              ▼                    ▼                    ▼
      │      deterministic         nutrition agent      report agent
      │      ratings engine        (what the client     (narratives, plan,
      │      (scores, focus,        says they eat)       readiness read)
      │       gap detection)              │                    │
      │              └────────────────────┴────────────────────┘
      │                                   │
      ◄──────────── stored report ────────┘
      │
  report viewer (coach / client voice) ── weekly check-in loop

Anything with a number in it is deterministic TypeScript: the rating scores, the focus-habit selection, the fat-loss timeline calculator, the self-awareness gap checks. The AI agents only ever interpret free text and write prose. They are never asked to invent a number, and the prompt forbids re-rating what the client already rated themselves.

Key Design Decisions

Decision · Hosting

Managed platform over self-built infrastructure. My other projects run on hand-built AWS: VPCs, ECS, Terraform. This one deliberately doesn't. Vercel hosts the Next.js app, Neon provides serverless Postgres in the Sydney region, Clerk handles coach auth, Resend sends the emails. Deploys are a git push, preview environments are free, and there is no instance anywhere that can fill a disk or miss a patch. For a one-person business tool, operational simplicity is the architecture. The tradeoff is platform lock-in, which I judged acceptable because every piece (Postgres, React, transactional email) is portable in substance even if the wiring is not.

Decision · Client access

Clients never get accounts. Asking a new coaching client to create a login before they've had a single session is friction in the worst possible place. Clients only ever touch tokenised public links. Intake links are single-use and expire after 14 days. Check-in links are deliberately the opposite: one reusable link per client that lives in their bookmarks, with revocation instead of expiry and a 20-hour double-submit guard. Two different token models for two different behaviours, each implemented as its own small validator rather than one generic system.

Decision · AI boundaries

Deterministic core, AI at the edges, independent failure. Each AI agent has one job and a typed tool schema: one estimates nutrition from the client's own food descriptions, one writes the report narratives, one reads weekly check-ins in context. Each call is wrapped so it can never throw away an intake: if an agent fails, the report still renders from the deterministic output with a visible "rules-based only" notice, and the failure is logged. The client's data is written before any AI runs.

Decision · Questions as content, not code

The question banks are markdown files. The 25 habit questions and 51 state questions live in two markdown files with stable keys, rubrics, and tags. The form, the engine, and the report all parse them at runtime. As the coach, I can reword a question, retire one, or add one without touching application code, and intake answers are stored as jsonb so question changes never need a migration. Retired questions keep labelling old answers instead of orphaning them.

Decision · Observability of the AI

Every AI call attempt writes a log row. Status, the exact prompt sent, raw tool output, token counts, duration, prompt version, and the provider request id. A coach-facing log viewer sits behind every report with a per-call cost estimate. When a report reads oddly, I can see precisely what the model was told and what it returned, and prompt versions make regressions diffable. This turned prompt iteration from guesswork into review.

Decision · One report, two voices

The report is authored in a coach voice and a client voice. The coach view is clinical third person and includes coach-only material (readiness assessment, self-awareness gaps where a client's self-rating contradicts their own numbers). The client view is second person and motivational, with those sections hidden. Both voices are produced in the same generation pass and stored on the same report, so they can never drift out of sync.

Where This Design Breaks Down

  • It assumes one coach. Data is scoped per coach, but there are no organisations, roles, or client sharing. Opening this to other coaches means real tenancy work, plus proper error alerting instead of reading Vercel logs.
  • jsonb answers trade queryability for flexibility. Question changes are free, but cross-client analytics ("average sleep rating across all clients") means walking json in SQL. If the practice grows, the hot fields get promoted to columns.
  • No automated alerting on AI degradation. A failed agent degrades gracefully and visibly in the report, but nothing pages me. Fine while I open every report myself; not fine with volume.

What I'd Do Differently

  • Test the email path on day one. Magic links shipped with a copy-to-clipboard fallback, so actual email delivery through Resend went unexercised for weeks. The fallback was so convenient it hid the untested path.
  • Trust the schema tool less on constraints. Drizzle's push silently skipped widening a CHECK constraint when a new value was added to an enum-like column, and the insert failed only at runtime. The fix was a manual ALTER in the database. Constraint changes now get verified against the live schema, not assumed from the ORM.
  • Design the intake as self-ratings from the start. Version one inferred habit quality from dozens of behavioural questions and a rules engine comparing clients to goal personas. It worked, but clients know where they stand: asking them to rate themselves 1 to 10 with a note produced a shorter form and a more honest report, and most of the inference engine was deleted. The lesson is old but real: the clever system I enjoyed building was not the simple system the product needed.
