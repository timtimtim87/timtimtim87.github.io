VPC Architecture

I built a three-tier VPC across three Availability Zones in us-east-1 (CIDR 10.20.0.0/16). Each tier has a distinct trust level enforced by both route tables and security groups.

TierSubnetsHostsInternet
Public 10.20.0.0/20, 10.20.16.0/20, 10.20.32.0/20 ALB, NAT Gateway Inbound + outbound via IGW
Private App 10.20.48.0/20, 10.20.64.0/20, 10.20.80.0/20 ECS Fargate tasks Outbound only via NAT Gateway
Private Data 10.20.96.0/20, 10.20.112.0/20, 10.20.128.0/20 ElastiCache Redis Outbound only via NAT Gateway (no inbound path)

Each /20 subnet provides 4,091 usable IP addresses (4,096 less the 5 that AWS reserves in every subnet). This is far more than the project needs, but oversizing has no practical cost in an isolated VPC. A tighter design would size subnets from the expected host count, and I would do that in a shared enterprise VPC where address space is allocated across teams.

Why Three Tiers?

Separating the tiers isolates resources by trust level. Security groups allow only expected traffic at each layer. Route tables in the private tiers route 0.0.0.0/0 to a NAT Gateway rather than an Internet Gateway. NAT is outbound-only, so there is no inbound internet path to ECS tasks or Redis even if a security group rule were misconfigured.

NAT Gateway Strategy

A single NAT Gateway handles outbound internet traffic from the private subnets. This creates a dependency on one AZ for egress. For higher resilience I would run a NAT Gateway in each AZ. The Terraform VPC module accepts nat_gateway_mode = "single" | "per_az", so switching to per-AZ NAT is a one-line change.

Security Groups

Security groups enforce a one-directional chain of trust. Each layer only accepts traffic from the layer directly above it. 

Internet (0.0.0.0/0)
  │  443 / 80
  ▼
ALB Security Group
  │  8080 (app container port)
  ▼
Fargate Task Security Group
  │  6379 (Redis)
  ▼
Redis Security Group

The Redis rule references the Fargate task security group ID rather than a CIDR block. Since Fargate tasks are ephemeral and get random IPs, any new task gets access automatically by being a member of that security group, so no IP management is needed as tasks scale.

VPC Endpoints

AWS API calls from Fargate tasks route through VPC Endpoints rather than the NAT Gateway. This avoids NAT data processing charges on ECR image pulls, CloudWatch log writes and Secrets Manager reads, and keeps that traffic inside the AWS network.

EndpointTypeCostPurpose
S3GatewayFreeECR image layer storage, static assets
DynamoDBGatewayFreeDatabase access from app tier
ECR APIInterface~$7/mo per AZContainer image metadata
ECR DockerInterface~$7/mo per AZContainer image pull
CloudWatch LogsInterface~$7/mo per AZApplication log delivery
Secrets ManagerInterface~$7/mo per AZRedis auth token at task startup

VPC endpoints could reduce NAT Gateway usage for AWS service traffic such as ECR pulls, CloudWatch Logs, Secrets Manager, S3, and DynamoDB. Gateway endpoints for S3 and DynamoDB are free, but interface endpoints have their own hourly and per-GB costs, so whether they save money depends on AZ count, endpoint count and actual traffic volume. The cost model below covers this in detail.

Terraform Structure

All infrastructure is defined in Terraform, with one module per AWS service boundary. The root main.tf wires modules together, passing outputs as inputs (e.g. VPC subnet IDs feed into ECS and ElastiCache). 

terraform/
├── modules/
│   ├── vpc/                  # VPC, subnets, IGW, NAT, route tables, endpoints
│   ├── ecs/                  # IAM task execution role and task role only
│   ├── ecs_compute/          # ECS cluster, task definition, service, ECR repo, SG
│   ├── alb/                  # ALB, target groups, listeners, ACM cert
│   ├── dynamodb/             # All DynamoDB tables and GSIs
│   ├── elasticache/          # Redis replication group, subnet group, param group
│   ├── cognito/              # User pool, app client, Google IdP
│   ├── route53/              # Hosted zone, alias records, ACM validation
│   ├── monitoring/           # CloudWatch alarms, dashboards, SNS, budgets
│   ├── static_edge/          # S3 bucket + CloudFront for chess-chat.com apex
│   └── github_actions_oidc/  # IAM OIDC provider + least-privilege deploy role
├── environments/dev/
│   └── terraform.tfvars
├── main.tf           # Module wiring
├── backend.tf        # S3 remote state config
└── versions.tf       # Provider version pins
The Redis and ECS modules appear to depend on each other, but this does not create a dependency cycle. Terraform builds its dependency graph per resource rather than per module. The Redis security group's ingress rule needs the ECS security group's ID, and the ECS task definition needs the ARN of the Redis auth-token secret. The security group and the secret are themselves independent resources, so Terraform creates both of them first. It then creates the ingress rule and the task definition, followed by the Fargate service and the Redis replication group.

Module Outputs as Inputs

Modules expose typed outputs that other modules consume directly. In ecs_compute/main.tf, the task definition takes its secrets list as a variable: 

resource "aws_security_group" "service" {
  count  = var.enabled ? 1 : 0
  name   = local.service_sg_name
  vpc_id = var.vpc_id
}

resource "aws_ecs_task_definition" "app" {
  count = var.enabled ? 1 : 0
  container_definitions = jsonencode([{
    # ...
    secrets = var.container_secrets   # Redis auth token flows in here
  }])
}

In elasticache/main.tf, the ingress rule takes the ECS security group's ID as a variable, and the auth-token secret depends only on a local random_password: 

resource "aws_security_group" "redis" {
  name   = local.security_group_name
  vpc_id = var.vpc_id
}

resource "aws_vpc_security_group_ingress_rule" "from_ecs_service" {
  count                         = var.enable_ecs_service_ingress ? 1 : 0
  security_group_id             = aws_security_group.redis.id
  referenced_security_group_id  = var.ecs_service_security_group_id
  from_port                     = var.port
  to_port                       = var.port
  ip_protocol                   = "tcp"
}

resource "aws_secretsmanager_secret" "redis_auth_token" {
  name                    = local.auth_secret_name
  recovery_window_in_days = 7
}

The root module wires the two together in both directions without forming a cycle, because each side only needs the other's leaf output: 

# In main.tf
locals {
  ecs_container_secrets_effective = concat(var.ecs_container_secrets, [{
    name      = "REDIS_AUTH_TOKEN"
    valueFrom = "${module.elasticache.redis_auth_secret_arn}:auth_token::"
  }])
}

module "ecs_compute" {
  source            = "./modules/ecs_compute"
  container_secrets = local.ecs_container_secrets_effective
}

module "elasticache" {
  source                        = "./modules/elasticache"
  ecs_service_security_group_id = module.ecs_compute.service_security_group_id
}

The Redis hostname itself isn't wired through Terraform this way. REDIS_HOST in terraform.tfvars.example is a plain string variable, pasted in manually after the first elasticache apply once the primary endpoint exists. The only coupling Terraform resolves automatically is the security group ID and the auth-token secret ARN, and neither of these creates a cycle.

Remote State

Terraform state is stored in S3 with versioning enabled and file-based locking (use_lockfile = true). State versioning means any previous infrastructure state can be restored from S3 version history if needed. 

# backend.tf
terraform {
  backend "s3" {
    bucket       = "chesschat-tfstate-xxxxxxxxxxxx-us-east-1"
    key          = "dev/terraform.tfstate"
    region       = "us-east-1"
    use_lockfile = true
  }
}

The state bucket name includes the AWS account ID to guarantee global uniqueness without a random suffix that would need to be tracked separately.

CI/CD Pipeline

GitHub Actions runs the pull request checks and the deployment. Authentication to AWS uses OIDC (OpenID Connect). An IAM role trusts GitHub's OIDC provider, and the workflow assumes that role for the duration of the pipeline run.

The deploy workflow uses workflow_dispatch, so it is triggered manually rather than on every push to main. I chose this deliberately. The stack cost real money to run and I was the only person making changes, so I wanted to decide when the running environment changed. On a team I would auto-deploy to staging on merge and keep the manual gate only in front of production.

Deploy pipeline steps (single job, sequential):

  1. Checkout source
  2. Configure AWS credentials via OIDC
  3. Login to Amazon ECR
  4. Build Docker image and push to ECR (commit SHA tag + main-latest tag)
  5. Generate config.js from GitHub Actions variables (Cognito IDs, app host, cookie config) and sync static auth assets to S3. config.js is uploaded with Cache-Control: no-store so Cognito config changes take effect immediately, while all other assets use a 5-minute CDN cache
  6. Trigger full CloudFront invalidation (/*)
  7. Register new ECS task definition revision
  8. Deploy ECS service and wait for stable state
  9. Upload deployment metadata artifact

Tests are not part of the deploy pipeline. Backend, frontend and Terraform quality checks run in PR workflows and are enforced as required status checks on main. Branch protection is configured with enforce_admins = true and required_conversation_resolution = true, with force-push and deletion disabled. I applied these branch protection settings through the GitHub API. They are not managed in Terraform.

Redis and DynamoDB Responsibilities

The platform uses two data stores with separate responsibilities. Redis holds short-lived session state: active room metadata, in-progress game state and the WebSocket connection map, all of which expire when the session ends. DynamoDB holds durable records: completed games, user profiles and stats, friend connections, and the persistent room code for each friend pair.

DynamoDB receives one transactional write per completed game, regardless of how many moves were played, because all mid-game state stays in Redis. DynamoDB costs therefore scale with the number of completed games rather than with in-game activity.

DynamoDB Schema

The schema uses a multi-table design, with one table per domain, rather than a single-table pattern. IAM permissions, CloudWatch metrics and PITR settings are simpler to manage per table. The social domain was also added after the initial design. Retrofitting single-table key namespacing would have been difficult, so separate tables gave me more room to extend the schema. To be transparent, Claude helped me design the schema from my application requirements.

Users

users
Keys
PK user_id (S) Cognito sub (immutable UUID)
Global Secondary Index
GSI username-index PK: username (S)
Attributes
username · display_name · email · chess_com_username · chess_com_verified
total_games · wins · losses · draws · created_at · last_login_at
Why user_id as PK, not username? Usernames can change. I planned a chess.com OAuth integration with a displacement mechanic, where a verified chess.com account holder could claim a username held by an unverified user. That feature did not eventuate. Keying on the immutable Cognito sub means a username change never alters a primary key, so it is a small transactional write in the users table (the user item and the username reservation items) rather than a data migration.

Games

games
Keys
PK game_id (S) UUID
SK ended_at (S) ISO 8601 timestamp string
Global Secondary Indexes
GSI 1 white-player-index PK: white_player_id · SK: ended_at
GSI 2 black-player-index PK: black_player_id · SK: ended_at
Attributes
white_player_id → users · black_player_id → users
winner · result · total_moves · duration_seconds · room_code
time_white_remaining · time_black_remaining · moves[] · fen_history[] · pgn
Why two GSIs? A player alternates colours across games, so their full history includes games where they were white and games where they were black. A GSI partition key maps to a single attribute, so one GSI cannot serve both lookups. Two GSIs, queried in parallel and merged in the application, cover both.

Friendships are written in both directions simultaneously (A→B and B→A), so listing a user's friends is a single Query PK=user_id with no GSI required. The Challenges table uses the same two-GSI pattern as Games, because a challenge involves two parties and must be visible to both. The pair_rooms table stores a persistent room code per friend pair. When a player challenges a friend, or starts a game with them by username from the lobby, the backend builds a deterministic pair_id (both user IDs sorted and joined) and looks up the room code for that pair. If none exists, it generates an 8-character code and writes it with a conditional PutItem, so two concurrent requests cannot create different codes for the same pair. Returning friends always get the same room code.

Redis Schema

Redis stores short-lived session state. Room and connection keys have a TTL, and all Redis data is treated as disposable. Losing it would end live sessions, but completed games and user data are held in DynamoDB. 

room:{room_code}          String (JSON-encoded), TTL 60min
  {
    status,               waiting | both_connected
    terminal,             true once teardown has started
    chime_meeting,        { meetingId, meetingData } once both players join
    participants,         per-user connection state
    active_game,          null if no game running
    games_played          array of completed game summaries
  }

ws:{connection_id}        String (JSON-encoded), TTL 60min
  { userId, roomCode }

room_expiries             Sorted Set (ZSET)
                          member: room_code, score: expiry Unix timestamp
                          Background worker scans for expired rooms

room_reconnect_deadlines  Sorted Set (ZSET)
                          member: room_code, score: reconnect grace deadline timestamp
                          Background worker scans for elapsed grace periods

game_finalization_queue   List: jobs awaiting DynamoDB write
game_finalization_deadletter  List: jobs that failed after 5 attempts

Room and connection state is stored as JSON strings using SET/GET rather than as Redis Hashes. WebSocket connection state is kept in Redis rather than in Fargate task memory, so any task can look up any connection. A Redis pub/sub relay for routing messages across multiple tasks, which I did not build, would rely on this.

The two sorted sets let a background worker scan for and act on expired rooms and elapsed reconnect grace periods, even when the originating WebSocket connection is gone. This is more reliable than relying only on Redis key TTLs, which do not trigger a callback when a key expires.

The finalisation queue is a Redis List used as a simple job queue. Completed game data waits there until it can be written to DynamoDB. If DynamoDB is momentarily unavailable, the job sits in the queue rather than being lost. Jobs that fail five times are parked in the dead letter list for inspection rather than retried indefinitely.

Data Flow

Room Creation

  1. User A challenges User B from the Friends page (REST POST /api/challenges) or enters User B's username in the lobby (REST GET /api/rooms/pair)
  2. Backend looks up the pair's room code in the pair_rooms table, or creates an 8-character code if the pair has never had one. A challenge is also stored with that code, and User B is sent a notification
  3. User A's browser opens /room/{code} and sends join_room over the WebSocket
  4. No room exists in Redis for that code, so the backend creates one (SET NX, 60-minute TTL) with status waiting
  5. User B joins the same code (for example by entering User A's username in the lobby, which resolves to the same pair code), and the room status becomes both_connected
  6. Backend creates the Chime SDK meeting and an attendee for each player
  7. Meeting and attendee details sent to both clients over the WebSocket (video_ready)
  8. Chime SDK initialises on both frontends and video starts

Chess Move

  1. Player drags a piece and chess.js validates the move locally, so the board responds immediately
  2. Move sent to backend via WebSocket: { move: "e2e4" }
  3. Backend validates the move with chess.js (the authoritative source of truth)
  4. Board FEN, move list and clocks updated in Redis
  5. Move broadcast to both clients as a move_made event that includes moveType and isCheck fields, so the server determines which sound plays
  6. Both frontends update the board and clocks and play the matching sound cue

Game Completion

  1. End condition detected (checkmate / resignation / timeout)
  2. Game metadata calculated (duration, time remaining, move count)
  3. Finalisation job pushed to a Redis List (game_finalization_queue), so the write is decoupled from the in-flight WebSocket session and survives a Fargate task crash
  4. Background worker pops the job and writes the game record to DynamoDB with a conditional put inside a TransactWriteItems call (idempotent, so safe to retry)
  5. Failed writes retry with exponential backoff (base 250 ms, up to 5 attempts). Jobs that fail all 5 attempts are pushed to game_finalization_deadletter
  6. The same transaction updates both players' win, loss and draw counts on the Users table
  7. Active game cleared from Redis room state
  8. game_ended event broadcast to both clients

Session Lifecycle

First player joins the pair's room code
  │  Redis room created (SET NX), status: waiting
  ▼
Second player joins
  │  status: both_connected, Chime meeting created
  ▼
Games played (unlimited sequential games)
  │  Each game: Redis active_game → DynamoDB via finalisation queue
  ▼
Player disconnects during a game
  │  12-second reconnect grace (tracked in room_reconnect_deadlines ZSET)
  │  Reconnect events carry a reconnectVersion. The frontend ignores
  │  updates with version ≤ last seen, preventing UI regression
  │  If grace expires, the disconnected player forfeits and teardown begins
  ▼
Both players leave, grace expires, or the 60-minute room window ends
  │  Active game (if any) ended and queued for DynamoDB write
  │  Room marked terminal: true via Redis WATCH/MULTI/EXEC (atomic)
  │  New join attempts rejected once terminal
  │  DEL room:{code} + ZREM from both sorted sets
  │  Chime meeting deleted (up to 3 attempts)
  ▼
Room session ended. The pair keeps its code in pair_rooms,
and the next join on that code creates a new Redis room.

The terminal state transition is atomic (Redis optimistic locking via WATCH/MULTI/EXEC). The cleanup that follows (DEL and removal from the two sorted sets) runs as separate commands after the transition is confirmed, and the Chime meeting is deleted after that. Join attempts that arrive while the room is terminal are rejected. Once the Redis key is deleted, the room code itself is not retired: it stays in pair_rooms, and the next time the same two players join it, the backend creates a fresh room in Redis.

WebSocket Routing

WebSocket connections require session affinity: a client must reach the same Fargate task to maintain its connection. The ALB target group has sticky sessions enabled (lb_cookie, 24-hour duration).

Scaling limit. WebSocket routing only supports a single ECS task. If I continued the project, I would add a Redis pub/sub message relay so that any task could relay messages to connections held by another task. Sticky sessions would then no longer be required for message delivery. This limit is documented in the repository.

Connection state is already stored in Redis rather than in task memory, so the relay would build on the existing data model.

Video Infrastructure

Current: Amazon Chime SDK

Chime SDK provides a managed WebRTC implementation. The server creates a meeting and issues attendee tokens, and the client SDK handles negotiation, STUN/TURN and media streams. Cost: $0.0017 per attendee-minute.

A 1-hour session with two players is 120 attendee-minutes, or $0.20 per session.

Next Step If Continued: Native WebRTC and Coturn

If I continued the project, I would replace Chime SDK with browser-native WebRTC and a self-hosted Coturn TURN server. Video cost would then be a flat EC2 instance fee instead of per-minute billing.

At $0.0017 per attendee-minute, a two-person session costs about $0.20 per hour, so an instance costing $15–30 per month breaks even at roughly 75–150 hours of video per month.

The order I would follow: replace Chime with WebRTC and a single Coturn instance, then add Coturn redundancy, then add regional TURN instances based on where users are.

IAM Role Separation

ECS uses two distinct IAM roles per task:

  • Task Execution Role: used by the ECS agent to pull the container image from ECR, write logs to CloudWatch, and fetch secrets from Secrets Manager at startup. The application code never uses this role.
  • Task Role: used by the application at runtime. Grants access to specific DynamoDB table ARNs, Chime SDK meeting operations, and ElastiCache describe operations. No wildcard resources.

Application Metrics

The backend service emits 8 custom application metrics to CloudWatch in the Chesschat/Dev namespace (src/services/metrics.js):

  • WsConnectionsOpened / WsConnectionsClosed
  • GamesStarted / GamesEnded
  • GamePersistSucceeded / GamePersistRetried / GamePersistFailed
  • AppErrors

These appear alongside infrastructure metrics on the CloudWatch operations dashboard. The three GamePersist* metrics track the finalisation worker, so retries and failed writes are visible without parsing logs.

Logging

Application logs are written to CloudWatch Logs (/ecs/chesschat/application) with 30-day retention. VPC Flow Logs capture all network traffic in a separate log group with the same retention.

Every HTTP request is assigned an x-correlation-id (the client-supplied value or a generated UUID), which is logged with the method, path, status and latency. WebSocket sessions are traced the same way using a sessionId and connectionId. When an alarm fires, I start from the correlation ID, find the matching log entries and trace the request end to end.

Fixed Costs

Roughly $163 of the $212 was fixed cost that ran whether or not anyone used the platform: VPC interface endpoints ($89.28), the NAT Gateway ($33.48), ElastiCache Redis with a primary and a replica ($23.81) and the ALB ($16.71). The NAT Gateway processed 0.025 GB of data but cost $33. The VPC endpoints processed 1.67 GB but cost $89. The ALB served negligible traffic but cost $17. These are the costs of the production patterns the stack uses (a multi-AZ network, private subnets and managed endpoints), and they apply even at development load.

The biggest surprise was the VPC interface endpoints. Interface endpoints are billed per AZ, so each endpoint deployed across three AZs incurs three hourly charges. Four endpoints across three AZs produce 12 endpoint-hours per clock hour rather than 4. At low data volumes, this makes interface endpoints much more expensive than routing the same traffic through NAT. The Gateway endpoints (S3 and DynamoDB) have no hourly charge, so they are not affected.

Cost at Higher Usage

The fixed costs stay flat while variable costs grow with usage. NAT data processing charges ($0.045/GB) and Fargate compute scale with real load, so at meaningful traffic the always-on baseline becomes a smaller share of total spend. The VPC endpoints also start to pay for themselves at higher volumes, because routing ECR pulls and CloudWatch log writes through endpoints avoids NAT data processing charges.

The stack uses production patterns (a multi-AZ network, private subnets, infrastructure as code and required PR checks), but it has documented limits that I would address before carrying real traffic: a single NAT Gateway, a single ECS task, and WebSocket routing that only supports one task.

Moving from Chime to WebRTC and Coturn would replace per-minute video billing with a flat EC2 instance cost, which suits a steady, predictable session volume.
